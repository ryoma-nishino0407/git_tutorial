API入出力まとめ、ありがとうございます。いただいた形式に沿って#34(AI判定・Dify側)の出力を実装しましたが、実装にあたり何点か確認させてください。

1. by_rule・by_ai・Scoreの値について

いただいた表を拝見すると、by_rule「本APIは常にtrue」・by_ai「本APIは常にfalse」・Score「コードで決定的に判定するため常に1.0」という説明は、コード側(決定的チェック)APIの挙動を指しているように読めました。

AI判定側(本Issue#34、Dify)では、これを反転させてby_rule=false・by_ai=true・Score=AIが算出した信頼度(0〜1の変動値)として実装しています。この解釈で合っているか確認させてください。

2. citationが複数件になるケースに対応していません

いただいた仕様は「検出した文字ごとに1件」と、1項目に対して複数件のcitationを想定された設計と理解していますが、現在のRAG構成では1項目につき根拠チャンクを上位1件のみ抽出する設計のため、citationは常に0件か1件にしかなりません。

この設計は、もともと#19時点でナレッジ検索ノード自体がTop K=1だったことに由来しており、その後#36のリランキング分離対応でTop3まで候補を取得できるようになった際も、根拠抽出ノード(②-b-2)側は「先頭1件のみ抽出」のロジックを維持したまま変更していません。

1件→3件に変更すること自体は技術的には可能ですが、単純な件数変更では済まない論点があると考えています。

現在、検索で見つかった3件のうち先頭1件だけが疑義判定LLM(②-b-3)に渡されています。3件すべて渡す場合、それらを疑義判定にどう使わせるか(全てを根拠として提示するのか、LLMに実際に使った候補を選ばせるのか)を設計し直す必要があります。
「検索で見つかった候補」と「疑義判定の根拠として実際に使った候補」を区別しないと、使っていない候補まで根拠として返してしまう可能性があり、#36の受入条件(存在しない根拠を補わない)に抵触しかねません。
以前ご報告した評価(#36)で見つかった「届出種別固有ルールと共通知識文書のどちらを正解とすべきか」という論点とも直結しており、複数候補のうちどれを採用すべきかの業務判断が先に必要になりそうです。

1件のまま進めてよいか、複数件対応が必要であれば上記のような設計変更を進めてよいか、ご意見をいただけますでしょうか。

3. konkyo_johoフィールドについて

いただいた仕様にはないフィールドですが、出典名・種別・版数・該当箇所・引用抜粋・関連度スコア・参照IDを持つkonkyo_johoを各gigi_check要素に追加しています。根拠の追跡可能性(#36の受入条件)のために残したいのですが、もしバックエンド側でgigi_check配列を厳格なスキーマ検証にかけている場合、想定外のフィールドとして問題になる可能性があります。このフィールドを残してよいか、別の場所(例えば別のレスポンスフィールド)に分離すべきか、確認させてください。

4. statusフィールドについて

いただいた仕様には存在しない概念ですが、本ワークフローはOCR項目リストの解析に失敗した場合のエラーハンドリングとして、status(「処理失敗」または「確認待ち」)を返却しています。現在はこれをgigi_check/msgとは別のレスポンスフィールドとして返す形にしています。この設計のままで問題ないか、あるいは決定的チェック側(コード)のAPIとエラーハンドリングの形式を合わせる必要があるか、教えてください。
